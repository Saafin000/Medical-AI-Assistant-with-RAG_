1. MULTI-AGENT SYSTEM OVERVIEW

Framework: LangGraph (state machine-based orchestration)
Entry Point: FastAPI endpoint /chat (app.py)
Routing: Agent Decision system in agents/agent_decision.py
State Management: MessagesState (conversation history + workflow state)
Database: Qdrant (vector store) + LocalFileStore (document metadata)
Configuration: Centralized in config.py (Config class)

2. CURRENT AGENTS

A. CONVERSATION_AGENT
   - Type: General dialogue
   - Model: ChatGroq (qwen/qwen3.8-27b, temperature=0.7)
   - Invoked by: Agent Decision when query is general conversation
   - Function: run_conversation_agent() in agent_decision.py:235

B. RAG_AGENT
   - Type: Knowledge retrieval + response generation
   - Class: MedicalRAG (agents/rag_agent/__init__.py)
   - Model: ChatGroq (qwen/qwen3.8-27b, temperature=0.3)
   - Components:
     * MedicalDocParser (Docling-based parsing)
     * ContentProcessor (chunking + embedding)
     * VectorStore (Qdrant integration)
     * Reranker (cross-encoder reranking)
     * QueryExpander (semantic expansion)
     * ResponseGenerator (LLM-based response)
   - Invoked by: Agent Decision when RAG_AGENT selected
   - Function: run_rag_agent() in agent_decision.py:319

C. WEB_SEARCH_PROCESSOR_AGENT
   - Type: Real-time medical information
   - Class: WebSearchProcessorAgent (agents/web_search_processor_agent/)
   - Model: ChatGroq (qwen/qwen3.8-27b, temperature=0.3)
   - Providers: DuckDuckGo (primary), PubMed (optional)
   - Invoked by: Agent Decision OR auto-fallback from RAG (low confidence)
   - Function: run_web_search_agent() in agent_decision.py

D. MEDICAL VISION AGENTS (Image Analysis)
   - BRAIN_TUMOR_AGENT: Brain MRI analysis
   - CHEST_XRAY_AGENT: Chest X-ray analysis
   - SKIN_LESION_AGENT: Skin lesion classification
   - Invoked by: Agent Decision when images uploaded
   - Requires: Human validation after analysis

   ├── current_input: str | Dict - User query

1. CONVERSATION FLOW WITH NEW CLINICAL AGENT

   User: "I'd like to prepare for my doctor's appointment"
       ↓
   Agent Decision → Routes to CLINICAL_PRE_CONSULTATION_AGENT
       ↓
   Clinical Agent Lifecycle:
   
   Phase 1: Patient Information Collection
   ├── Greeting & consent
   ├── Demographic collection
   │   └── Follow-up: "What's your name, age, and gender?"
   ├── Chief complaint identification
   │   └── Follow-up: "What brought you here today?"
   └── Response: "I'll help you prepare. Let me ask you some questions..."
   
   Phase 2: Symptom & History Collection (Adaptive Questioning)
   ├── Initial symptom question: "Can you describe your symptoms?"
   ├── Analyze response → Identify gaps
   ├── Generate follow-up: "When did this start?", "Has it gotten worse?"
   ├── Collect: Duration, severity, progression
   ├── Collect: Medical history, medications, allergies
   ├── Collect: Lifestyle factors (smoking, alcohol, exercise)
   └── Dynamic adjustment based on responses
   
   Phase 3: Context Enhancement
   ├── Query RAG Agent: "Provide information about [patient's symptoms]"
   │   └── Returns: Relevant medical knowledge from ingested documents
   ├── Query Web Search Agent: "Recent developments in [condition/treatment]"
   │   └── Returns: Latest medical information
   └── Integrate context into patient data
   
   Phase 4: Red Flag Detection
   ├── Analyze collected symptoms + vitals
   ├── Detect CRITICAL flags: "severe chest pain", "difficulty breathing"
   │   └── Generate: Urgent guidance, suggest emergency care
   ├── Detect HIGH flags: Symptoms requiring specialist
   │   └── Generate: Escalation recommendation
   └── Store flags for doctor notification
   
   Phase 5: Report Generation
   ├── Compile all data:
   │   ├── Patient demographics
   │   ├── Chief complaint
   │   ├── Symptom details
   │   ├── Medical history
   │   ├── Current medications
   │   ├── Allergies
   │   ├── Vital signs (if available)
   │   └── Red flags (if any)
   ├── Format for doctor: Structured pre-consultation report
   ├── Include context: Medical knowledge from RAG/Web Search
   ├── Include gaps: "Missing information: recent lab results"
   └── Save to database
   
   User receives: "Your pre-consultation report is ready. [Summary]"

================================================================================

1. ARCHITECTURAL RISKS

Risk: Agent State Explosion
├─ Problem: Adding new agent increases message history size
├─ Impact: Memory usage, LangGraph performance
├─ Mitigation:
│  ├─ Clinical agent runs independently with separate state (optional)
│  ├─ Implement message history truncation (already in place)
│  └─ Monitor state size in production

Risk: Conversation Context Confusion
├─ Problem: Patient info collection may interfere with RAG/Web Search calls
├─ Impact: LLM may misinterpret context
├─ Mitigation:
│  ├─ Use separate LLM context for agent-to-agent communication
│  ├─ Explicitly mark internal vs. external queries
│  └─ Isolate agent communication from user conversation

Risk: Concurrent Agent Calls
├─ Problem: Clinical agent requests RAG + Web Search simultaneously
├─ Impact: May exceed API rate limits
├─ Mitigation:
│  ├─ Sequential calls (safer, but slower)
│  ├─ Implement request queuing
│  └─ Add API rate limit handling

2. COMPATIBILITY RISKS

Risk: Existing RAG Agent Modification
├─ Problem: Clinical agent must NOT modify MedicalRAG internal state
├─ Impact: Could affect retrieval quality for main system
├─ Mitigation: ✓ READ-ONLY access to RAG Agent
│  ├─ Clinical agent calls: rag_agent.process_query() only
│  ├─ No modification of: vectorstore, docstore, embeddings
│  └─ No ingestion or configuration changes

Risk: Existing Web Search Agent Modification
├─ Problem: Clinical agent must NOT modify WebSearchProcessorAgent
├─ Impact: Could affect search results for main system
├─ Mitigation: ✓ READ-ONLY access to Web Search Agent
│  ├─ Clinical agent calls: web_search_agent.search() only
│  ├─ No modification of: search parameters, providers, caching
│  └─ No configuration changes

Risk: Existing Conversation Agent Interference
├─ Problem: User may ask clinical questions to Conversation Agent
├─ Impact: Clinical agent never called if user doesn't explicitly request
├─ Mitigation:
│  ├─ Update Decision System prompt to offer clinical intake
│  ├─ Add keywords for clinical agent routing
│  └─ No change to Conversation Agent code

Risk: Existing Vision Agents Not Affected
├─ Status: ✓ No compatibility issues
├─ Reason: Clinical agent and vision agents are independent
├─ Note: Can be enhanced later for integrated vision+intake workflow

3. DATA INTEGRITY RISKS

Risk: Patient Data Privacy & Security
├─ Problem: Storing patient data locally
├─ Impact: Privacy violation if not properly secured
├─ Mitigation:
│  ├─ Use encrypted SQLite (implement later)
│  ├─ Session-based isolation
│  ├─ No persistent identification unless explicitly provided
│  └─ HIPAA compliance guidance (if needed)

Risk: Database Integrity During Concurrent Writes
├─ Problem: Multiple sessions writing simultaneously
├─ Impact: Data corruption, race conditions
├─ Mitigation:
│  ├─ SQLite has built-in locking (safe for single process)
│  ├─ Add transaction support in PatientSessionStore
│  ├─ Implement session-level atomicity
│  └─ Test with concurrent access patterns

Risk: Report Inconsistency
├─ Problem: Patient data may be incomplete when report generated
├─ Impact: Doctor misses critical information
├─ Mitigation:
│  ├─ Add "Missing Information" section to report (prevents misinterpretation)
│  ├─ Implement report versioning (track updates)
│  ├─ Allow report finalization (prevents mid-generation access)
│  └─ Doctor confirmation workflow

4. LLM-SPECIFIC RISKS

Risk: Groq API Rate Limiting with Multiple Agents
├─ Problem: Clinical agent + RAG + Web Search all use same Groq API
├─ Impact: Could trigger 429 errors
├─ Mitigation:
│  ├─ Sequential requests (current approach)
│  ├─ Implement exponential backoff
│  ├─ Add API error handling with user feedback
│  └─ Monitor Groq usage across all agents

Risk: LLM Hallucinations in Red Flag Detection
├─ Problem: LLM may false-positive or false-negative on emergencies
├─ Impact: Missed critical conditions or unnecessary escalation
├─ Mitigation:
│  ├─ Use keyword-based detection (rule-based, not just LLM)
│  ├─ Low temperature (0.5) for consistency
│  ├─ Multiple validation layers
│  └─ Always recommend: "Consult healthcare professional"

Risk: Context Length Limits
├─ Problem: Patient history + medical context may exceed LLM token limit
├─ Impact: Truncated context, incomplete analysis
├─ Mitigation:
│  ├─ Set context_limit in config (currently 30 messages)
│  ├─ Implement summarization for long histories (future)
│  ├─ Prioritize recent data over old
│  └─ Monitor token usage
