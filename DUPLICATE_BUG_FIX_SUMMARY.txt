================================================================================
DUPLICATE-PROCESSING BUG FIX - COMPLETE SUMMARY
================================================================================

CRITICAL BUG (NOW FIXED):
- Oversized sections were split into multiple pieces
- OLD batching stored duplicate section indices: [[0, 1], [2], [2], [3, 4]]
- chunk_document() expanded EACH occurrence of [2], sending both pieces TWICE
- Result: pieces submitted to LLM multiple times (data duplication, TPM waste)

ROOT CAUSE:
  In _create_batches(), for each split piece, code appended [idx] to batches:
    for piece_idx in range(len(split_pieces)):
        batches.append([idx])  # BUG: Creates duplicate [2], [2] in batches
  
  Then chunk_document() did:
    for idx in batch_indices:
        if idx in self.split_sections_cache:
            batch_sections.extend(self.split_sections_cache[idx])  # ALL pieces
  
  So [2] always expanded to ["piece1", "piece2"], duplicated in each batch.

================================================================================
FIX IMPLEMENTED
================================================================================

NEW APPROACH: Tuple-Based Work Items

Instead of storing section indices, store (section_idx, piece_idx) tuples.
Each tuple represents ONE piece of work and appears in EXACTLY ONE batch.

BEFORE (buggy):
  Batch 1: [2]      ← Just the section index
  Batch 2: [2]      ← Same index again (DUP LICATE!)
  
  chunk_document expands [2]:
    Batch 1 expands [2] → ["piece1", "piece2"]
    Batch 2 expands [2] → ["piece1", "piece2"]  (SENT AGAIN!)

AFTER (fixed):
  Batch 1: [(2, 0), (2, 1)]  ← Both pieces in ONE batch
  
  chunk_document expands tuples:
    (2, 0) → "piece1"    (sent once)
    (2, 1) → "piece2"    (sent once)

   - Binary split preserves all work items (no loss)

   - Handles both integer indices and tuples

================================================================================
KEY DESIGN DECISIONS
================================================================================

Decision 1: Tuple Format (section_idx, piece_idx)
  - Uniquely identifies each work item
  - No duplicates across batches
  - Easy to expand to actual piece content
  ✓ Chosen: Safe, clean, composable

Decision 2: Split Pieces in Same or Separate Batches
  ✓ Chosen: Depends on token budget
    - If pieces fit in one batch, keep together
    - If not, split into multiple batches
    - Maximizes context window usage, respects TPM limits

Decision 3: Mapping to Global Section IDs
  ✓ Chosen: Extract section_idx from tuple, use that
    - Simpler than storing separate mappings
    - Automatic deduplication for split sections
